## Méthode

- `list_edge_functions` (MCP, lecture seule) : slug, `verify_jwt` réel, version, `updated_at`.
- `get_edge_function` : rapatriement des sources prod (tous fichiers, `deno.json` compris).
- Appelants réels : grep `functions.invoke` / `functions/v1` dans `src/` + `app/`,
  `SELECT` sur `cron.job` (pg_cron) et sur `pg_proc` (fonctions SQL faisant du `net.http_post`).
- Auth analysée : lecture du handler de chaque fonction (garde interne réelle, pas la doc).
- Aucune mutation prod. La présence effective des secrets edge (`EDGE_FUNCTIONS_INVOKE_SECRET`,
  `CRON_TOKEN`, `RESEND_API_KEY`, …) n'est **pas vérifiable en lecture seule** — les gardes
  « fail-closed » ci-dessous renvoient 503 si le secret est absent, les « fail-open » laissent passer.

## Découvertes (à traiter, hors du présent inventaire)

1. **`ritual_dispatcher` : garde forgeable.** Le handler « authentifie » en décodant le payload du
   JWT sans vérifier la signature (`index.ts:43-54`). N'importe qui peut forger un token à trois
   segments dont le payload contient `{"role":"service_role","ref":"fouvuqkdxarjpjbqnsjq"}` et
   déclencher l'envoi de vrais e-mails aux pilotes. Le commentaire du code (« c'est qu'il a été
   signé par les clés de Supabase ») est faux.
2. **Clé service_role en clair dans `cron.job`.** Le job `ritual_dispatcher_hourly` (jobid 3)
   embarque le JWT service_role complet (claim `role=service_role`, expiration 2036) directement
   dans la commande cron, au lieu de le lire dans le Vault comme les jobs 4/5/7/8. Toute personne
   ou fonction capable de lire `cron.job` lit la clé maîtresse du projet.
3. **Divergence config.toml ↔ prod.** Le repo déclare `verify_jwt=true` pour
   `notify-pilot-coach-assigned` et `notify-coach-consent-received` ; la prod est à `false`
   (fail-open interne). C'est l'écart que l'Action 2 du lot SEC-1 prépare — le redéploiement
   reste à faire approuver.
4. **`validate-inscription` v12 (prod du 18/07)** embarque des arbitrages fondateur récents
   (coach opérationnel dès validation, compte partenaire `validated`) qui n'existaient dans
   aucun repo jusqu'à ce rapatriement.
5. **`compute-session-insights-v3`** est déployée ACTIVE sans aucun appelant identifiable —
   fonction orpheline à décommissionner ou à câbler explicitement.

## Edges à durcir (candidates fail-closed, au-delà des 2 du lot)

Par ordre de priorité :

1. **`ritual_dispatcher`** — remplacer le pseudo-contrôle JWT par la comparaison stricte à un
   secret Vault (pattern `send-document-status:81-83`) ; en même temps, migrer le job cron 3
   vers le Vault et **retirer la service_role key de `cron.job`** (rotation de la clé à évaluer).
2. **`cron-analyze-pending-sessions`** — rendre `CRON_TOKEN` obligatoire : 503 si absent,
   401 si mauvais (aujourd'hui : public si le secret n'est pas posé, verify_jwt=false).
3. **Les 4 notify-\* triggers** (`notify-pilot-coach-annotated`, `notify-coach-session-analyzed`,
   `notify-pilot-friend-request`, `notify-pilot-friend-accepted`) — passer la garde secret de
   fail-open (warn + continue) à fail-closed.
4. **`compute-session-insights` / `compute-session-insights-v3` / `generate-debrief-ai`** —
   ajouter un contrôle de propriété : le `sessionId` doit appartenir à l'appelant (ou appelant
   admin / token cron). Aujourd'hui tout utilisateur authentifié écrit chez les autres.
5. **`detect-circuit-corners`** — exiger le rôle admin dans le handler (verify_jwt=true ne
   filtre que l'anonyme, pas le pilote lambda).
6. **`geocode`** — faible : restreindre aux rôles partner/admin ou poser un rate-limit.
